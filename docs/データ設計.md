# Tri-Tri データ設計(DynamoDB)

> DynamoDB は「どの画面で、何を、どう読むか」を先に決めてからキーを決める。下の「アクセスパターン」がすべて、Scan を使わずに Query / GetItem / TransactWrite で行えることを確かめた。

## テーブル
### Main テーブル(1 テーブルに全種類を入れる)
- キー: `PK`(パーティションキー)、`SK`(ソートキー)
- GSI1: `GSI1PK`、`GSI1SK`(「自分の旅の一覧」と「承認待ちの旅」用。GSI1SK の前置き `TRIP#` / `JOINREQ#` で区別する)

| 種類 | PK | SK | GSI1PK / GSI1SK | 主な項目 |
|---|---|---|---|---|
| 会員 | `USER#<userId>` | `PROFILE` | — | displayName、deletedAt |
| 旅 | `TRIP#<tripId>` | `META` | — | title、startDate、endDate、destination、ownerId、memberCount、joinRequestCount、itemCount、ideaCount、expenseCount、commentCount(旅全体のコメントの件数)、dayCount(日数)、planRev(予定の配置の版)、inviteToken、inviteExpiresAt、publicToken |
| 参加申請 | `TRIP#<tripId>` | `JOINREQ#<userId>` | `USER#<userId>` / `JOINREQ#<requestedAt>#<tripId>` | tripId、displayName、requestedAt |
| メンバー | `TRIP#<tripId>` | `MEMBER#<userId>` | `USER#<userId>` / `TRIP#<joinedAt>#<tripId>` | role(owner/member)、displayName、joinedAt、withdrawn(退会した人。旅は開けず、GSI1 のキーも外す) |
| 予定 | `TRIP#<tripId>` | `ITEM#<itemId>` | — | day(何日目)、order、time、title、place{placeId, label}、memo、version、updatedBy、updatedAt、commentCount(コメントの件数。version は変えない) |
| 候補 | `TRIP#<tripId>` | `IDEA#<ideaId>` | — | name、place、note、createdBy、createdAt、adoptedItemId(採用するまで項目ごと持たない) |
| 投票 | `TRIP#<tripId>` | `VOTE#<ideaId>#<userId>` | — | ideaId、userId、votedAt。票数は VOTE の数から数える(別に数を持たないので、ずれない) |
| 支出 | `TRIP#<tripId>` | `EXP#<expenseId>` | — | title、amount(円・整数)、paidBy、splitWith[]、createdBy、createdAt |
| コメント | `TRIP#<tripId>` | `CMT#<itemId>#<commentId>` | — | itemId、body、userId、createdAt(名前は表示のたびにメンバー情報から引く。メンバーでなくなった人は「元メンバー」) |
| 招待リンク | `INVITE#<token>` | `INVITE` | — | tripId、expiresAt、ttl(DynamoDB の自動削除用。削除は遅れることがあるので、期限は必ずコードでも確かめる) |
| 公開リンク | `PUBLIC#<token>` | `PUBLIC` | — | tripId |

- ID は ULID(時刻順に並ぶ)を使う。
- 場所 `place` に持つのは `placeId`(Google の場所の ID)と `label`(利用者が入力した表示名)だけ。**座標・Google の名前・住所・経路・移動時間は保存しない**([Places API の方針](https://developers.google.com/maps/documentation/places/web-service/policies): ずっと保存してよいのは ID。座標は 30 日まで)。API は、それ以外の項目が入った場所を 400 で断る。座標は画面が表示のたびに ID から取り、メモリにだけ持つ。
- 件数の上限は META・ITEM の数(itemCount など)を、作成と同じトランザクションで条件つきで増やして守る。減らすときは「META・ITEM がまだあること」を条件にする(消えた旅・予定を作り直さないように)。
- 上限: メンバー 50 人、未処理の参加申請 50 件、予定 300 件、候補 100 件、支出 500 件(1 件 1000 万円まで)。コメントは 1 つの予定に 200 件。
- 予定の並び順 `order` は、間に挟める文字列(fractional index)にする。並べ替えでは動かした 1 件だけを書き換える。
- 予定を別の日へ動かしても、キーは変えない(`day` を書き換えるだけ)。キーを変えると「削除+作成」になり、楽観ロックが効かなくなるため。
- メンバーの表示名は `MEMBER` にも写しておく(旅の画面を 1 回の Query で出すため)。表示名の変更時に、GSI1 で自分の旅を引いて書き換える。

### Connections テーブル(WebSocket の接続)
| PK | SK | 主な項目 |
|---|---|---|
| `TRIP#<tripId>` | `CONN#<connectionId>` | connectionId、tripId、userId、lastSeen、editingItemId(編集中の予定)、ttl |
| `CONN#<connectionId>` | `CONN` | tripId(受信・切断時に旅を引くため)、ttl |
| `TRIP#<tripId>` | `SEQ` | seq(「今見ている人」の知らせの通し番号。追い越された古い知らせを画面で捨てる)、ttl |
| `TICKET#<ticket>` | `TICKET` | tripId、userId、expiresAt、ttl。30 秒・1 回限り |

- 表示名は写さない。送るときに Main テーブルの MEMBER から引く(表示名の変更がすぐ反映される)。
- 画面は 60 秒ごとに ping。150 秒音沙汰のない接続は、いないものとして消す。`ttl`(2 時間)は最後の掃除。
- チケットは `attribute_exists` の条件つきで消しながら読む(条件が無いと、同時に使われたとき 2 本つながる)。

## アクセスパターン
| # | 画面 | 操作 | やり方 |
|---|---|---|---|
| A1 | S05 | 自分の旅の一覧 | GSI1 を `GSI1PK = USER#<userId>`、`GSI1SK begins_with TRIP#` で Query → 各旅の META を BatchGet。承認待ちの旅は `begins_with JOINREQ#` で同様に(タイトルだけ返す) |
| A2 | S06 | 旅の作成 | TransactWrite: META + オーナーの MEMBER + INVITE |
| A3 | S07 | 旅の画面を開く | `PK = TRIP#<tripId>` で Query 1 回(META・メンバー・予定・候補・投票・支出・コメントをまとめて取る) |
| A4 | S07 | メンバーか確かめる | GetItem `TRIP#<tripId>` / `MEMBER#<userId>`。`/trips/:tripId` 以下の全 API に共通のミドルウェアで行う |
| A5 | S08 | 招待リンクを開く | GetItem `INVITE#<token>`(`expiresAt` を確かめる)→ META と、自分の MEMBER / JOINREQ を BatchGet |
| A5b | S08 | 参加申請 | TransactWrite: JOINREQ を作る(`attribute_not_exists`)+ META の `joinRequestCount` を +1(条件 `joinRequestCount < 50`)。MEMBER があれば 409 |
| A5c | S07 | 申請の一覧(オーナー) | `PK = TRIP#<tripId>`、`SK begins_with JOINREQ#` で Query |
| A5d | S07 | 承認(オーナー) | TransactWrite: JOINREQ を削除(`attribute_exists`)+ MEMBER を作る(`attribute_not_exists`)+ META の `memberCount` +1(条件 `memberCount < 50`)・`joinRequestCount` −1 |
| A5e | S07 | 却下(オーナー) | TransactWrite: JOINREQ を削除(`attribute_exists`)+ `joinRequestCount` −1 |
| A6 | S07 | 予定の追加 | TransactWrite: ITEM を作る(`attribute_not_exists`)、version = 1 + META の `itemCount` を +1・`planRev` を +1(条件 `itemCount < 300` かつ `dayCount >= day`)。日程の外・上限なら、META を読み直してどちらかを返す |
| A7 | S07 | 予定の更新・並べ替え | UpdateItem(条件 `version = 送られてきた version`)、version + 1。日を変えるときは TransactWrite で META の `planRev` を +1(条件 `dayCount >= day`)。条件に合わなければ 409 と今の内容(誰が変えたか)を返す。並び順のキーは画面側で前後の予定の間に作る(fractional-indexing) |
| A8 | S07 | 予定の削除 | TransactWrite: ITEM の削除(条件 `version` と `commentCount` が読んだときと一致)+ META の `itemCount` −1・`commentCount` −(その予定のコメント数)・`planRev` +1。その後、その予定のコメントを `CMT#<itemId>#` で Query してまとめて削除(消し残しても画面には出ない) |
| A9 | S07 | 候補を出す・消す | TransactWrite: IDEA + `ideaCount`。消すのは出した本人かオーナーで、その候補の VOTE も同じトランザクションで消す(投票は最大 50 件なので収まる) |
| A10 | S07 | 投票・取り消し | TransactWrite: VOTE を作る(`attribute_not_exists`)+ IDEA があることの確認(ConditionCheck)。取り消しは VOTE を消すだけ |
| A11 | S07 | 候補の採用 | TransactWrite: ITEM を作る + `itemCount` +1 + IDEA に `adoptedItemId` を入れる(条件 `attribute_not_exists(adoptedItemId)`) |
| A12 | S07 | 支出・コメントの追加・削除 | 支出: TransactWrite で EXP + `expenseCount`。払った人・分け合う人は今のメンバーだけ。削除はメンバーなら誰でも。コメント: TransactWrite で CMT + ITEM の `commentCount`(予定があることも確かめる)。削除は書いた本人だけ |
| A13 | S10 | 公開しおり | GetItem `PUBLIC#<token>` → A3 と同じ Query。旅の基本情報・メンバーの表示名・予定だけを返す(userId・updatedBy・割り勘・コメント・候補・招待は返さない) |
| A14 | S09 | オーナーの引き継ぎ | TransactWrite: 自分と相手の MEMBER の role を入れ替え + META の ownerId(条件 `ownerId = 自分`) |
| A15 | S09 | メンバーが抜ける・外される | TransactWrite: MEMBER の削除(条件 role = member)+ `memberCount` を −1。オーナーは抜けられない(先に引き継ぐ)。その人の支出・投票・コメントは残す |
| A15b | S09 | 旅の情報の変更・旅の削除 | 変更: 予定のある日より短くできない。読んだときから `planRev` が変わっていないことを条件に書き、変わっていたら読み直す(予定の追加・移動と同時でも日程の外に残さない)。削除: META を先に消して(条件 `ownerId = 自分`)すぐ見えなくし、INVITE・PUBLIC を消して応答する。残りの項目は後で片付ける(手元は応答の後、Lambda は今は応答の前。公開時に別の仕組みへ) |
| A15c | S11 | 表示名の変更 | PROFILE を書き換え、GSI1 で自分の MEMBER・JOINREQ を引いて displayName を書き換える |
| A16 | S09 | 招待・公開リンクの発行し直し・停止 | TransactWrite: 古い INVITE/PUBLIC を消す + 新しいものを作る + META を書き換える |
| A17 | S11 | 退会 | オーナーの旅は先に自動で引き継ぐ(最も早く参加したメンバーから順に、引き継げるまで)。1 人だけの旅は残す。PROFILE に `deletedAt`、各 MEMBER を `withdrawn`・displayName「退会した会員」にし、GSI1 のキーを外す(一覧に出ず、同じ ID で登録し直しても前の旅は見えない)。未処理の JOINREQ は消す。Cognito のユーザーの削除は AWS につなぐ段階で足す |
| A18 | — | 変更を全員に届ける | `/trips/:tripId` 以下の GET 以外が成功したら、共通のミドルウェアで通知(旅の URL の外の `POST /join/:token`・`PUT /me`・`DELETE /me` は個別)。SEQ を +1 → Connections を Query → 今のメンバーと照合(違えば `revoked` を送って切る)→ `changed`(合図だけ)と `presence` を送る。送れない接続(410)は消す。画面は A3 で読み直すので、A3・A4 は強い整合性で読む |
| A18b | S07 | WebSocket につなぐ | A4 の確認の後にチケットを発行 → 接続時にチケットを消しながら読み、期限・今もメンバーか・Origin を確かめて CONN を 2 件作る |

## テストで確かめる条件(TDD のテスト一覧)
API の結合テスト(DynamoDB Local)で、先にこれらを失敗するテストとして書いてから実装する。

### 権限(API を足すたびに、その API でも確かめる)
- [x] ログインしていないと、公開しおり以外の API はすべて 401
- [x] メンバーでない旅の API は、旅が無いときと同じ 404(旅があることを知られない)
- [x] オーナー専用の操作をメンバーが行うと 403
- [x] 公開しおりの API は、割り勘とコメントを返さない。止めたリンクは 404
- [x] 全 API を自動で列挙し、未ログインは 401、メンバー以外は 404 になることを確かめる(API を足すと自動でテスト対象になる)
- [x] 本番の入口では、テスト用のヘッダーで利用者を名乗れない(JWT の sub だけを使う)
- [x] 旅の一覧の応答に招待リンクのトークンを含めない

### 招待と参加申請
- [x] 申請しただけでは旅を開けない(404)。オーナーが承認するとメンバーになり、開ける
- [x] 却下すると申請が消え、旅は開けないまま
- [x] 2 回申請しても 1 件。参加済みの人の申請は 409
- [x] メンバー(オーナー以外)は、承認・却下・リンクの発行し直し・停止ができない(403)
- [x] 7 日を過ぎたリンク・停止したリンク・発行し直す前のリンクは、存在しないリンクと同じ 404
- [x] 招待リンクの画面には、旅のタイトル・メンバー数・自分の状態しか出ない
- [x] 50 人の旅では承認できない。49 人の旅で 2 件を同時に承認しても 50 人を超えない
- [x] 未処理の申請が 50 件ある旅には、それ以上申請できない

### 同時編集
- [x] 正しい version での更新は成功し、version が 1 増える
- [x] 古い version での更新は 409 で、今の内容が返る
- [x] 2 人が同じ version から同時に更新すると、片方だけ成功する
- [x] 並べ替えで、動かした予定以外は書き換えない
- [x] 予定は 1 つの旅に 300 件まで(META の itemCount を同じトランザクションで数える)。消すと空きができる
- [x] URL の旅と違う旅の予定 ID を指定しても触れない(キーに旅の ID が入っている)

### 場所
- [x] 場所は placeId と label だけ。座標や Google の名前が入っていたら 400
- [x] ID が無い・空、表示名が空なら 400

### 投票・採用
- [x] 同じ候補に 2 回投票しても 1 票。同時に 2 回押しても 1 票
- [x] 取り消すと票数が減る。投票していないのに取り消しても票数は減らない
- [x] 同じ候補を 2 人が同時に採用しても、予定は 1 件だけできる

### 割り勘(画面とも共通の計算。純粋な関数として単体テスト)
- [x] 全員が同じ額を払ったら、精算は 0 件
- [x] 割り切れない額の端数は、払った人の負担になる
- [x] 送金の回数が「人数 − 1」回以下になる
- [x] 抜けたメンバーの支出も精算に含まれる(API の結合テストで確認)

### 品質チェックで足した条件(2026-11-23)
- [x] 同時の書き込みが続いても 500 にせず 503 BUSY。想定外の失敗は JSON の 500 で、内部の情報を出さない
- [x] 招待・公開リンクの同時の発行し直しで 500 にならない(読み直してやり直す)
- [x] 日程の短縮と、予定の追加・移動が重なっても、日程の外に予定が残らない
- [x] 退会した人は旅を読めず書けない。同じ ID で登録し直しても前の旅は見えない。オーナーを引き継げない
- [x] 退会の引き継ぎ先が同時に抜けたら、次の人に引き継ぐ。抜ける操作と引き継ぎが重なったら 409
- [x] 投票が 100 を超えた候補も消せる。一度も無い件数を減らしても 500 にならない
- [x] 長すぎる ID は DB に問い合わせずに 404
- [x] 旅全体のコメントは 2,000 件まで。コメント・予定を消すと件数も減る
- [x] 旅の削除は、開けなくした所で応答し、残りは後で片付ける

### オーナーと退会
- [x] オーナーは引き継ぐ前に抜けられない
- [x] 引き継ぐと、前のオーナーはメンバーになる
- [x] オーナーが退会すると、最も早く参加したメンバーがオーナーになる
- [x] 1 人だけの旅は、退会しても残り、公開リンクで見られる。名前は「退会した会員」

### リアルタイム
- [x] 予定を変えると、同じ旅に接続している全員に届き、別の旅の接続には届かない
- [x] 切れている接続に送ろうとしたら、その接続を消す
- [x] 変更する API を自動で列挙し、すべてが 1 回だけ通知する(API を足すと自動でテスト対象になる)
- [x] チケットは 30 秒・1 回限り。同時に使っても 1 本だけつながる。外された人のチケットは使えない
- [x] 外された・抜けた・退会した・旅が削除されたら、変更の合図を送らずに切る
- [x] よそのサイト(Origin 違い)からの接続は、チケットを使わずに 403
- [x] 通知に失敗しても保存は成功する

## AWS でのリアルタイム更新
手元では開発用サーバー(`api/src/realtime/local.ts`)が WebSocket を受ける。本番は API Gateway WebSocket と Lambda で、同じ `realtime/service.ts` を使う。
- 入口: `api/src/ws-lambda.ts` → `realtime/ws-handler.ts`。$connect で Origin(画面の場所)と 1 回限りのチケットを確かめ、$disconnect で片付け、$default で受け取る(1 回 4KB まで。文字だけ)
- 送る部品: `realtime/apigw.ts`(PostToConnection。410 は "gone"、切るときは DeleteConnection)
- 設定: Lambda の環境変数 `TABLE_NAME`・`WEB_ORIGIN`・`CONNECTIONS_TABLE`・`WS_ENDPOINT`(管理用の https の URL)。半分だけの設定では起動しない(`api/src/aws-config.ts`)
- 画面の接続先: `NUXT_PUBLIC_WS_URL`(wss://…)。空なら API の場所の `/ws`
- $connect の最中の接続へ送ると 410 になり、その接続は消される。その接続は次の ping で切られ、画面がチケットを取り直してつなぎ直す

公開時に CDK で行うこと: Connections テーブルの TTL(`ttl`)の有効化、接続 URL の記録(アクセスログ)にチケットを残さない設定。旅の削除の後片付けは、今は Lambda の中で待ってから応答する(SQS などへ移すのは今後の課題)
