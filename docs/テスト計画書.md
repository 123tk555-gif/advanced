# Tri-Tri テスト計画書

> 作成日: 2026-11-22。合格基準は計測の前に定めた。計測の結果を見てから基準を緩めることはしない。結果は「テスト結果報告書」に記録する。

## 1. 目的
Tri-Tri(複数人で 1 つの旅のしおりを同時に作る Web アプリ)について、次の 2 点を確かめる。

1. **E2E テスト**: 利用者が画面から行う操作が、画面・API・データベースを通して正しく動くこと
2. **負荷試験**: 多人数が同時に使っても、遅くなりすぎず、データが壊れないこと。また、どこまで耐えられるか

## 2. 対象と対象外

| 区分 | 内容 |
|---|---|
| 対象 | 旅の一覧・作成・旅の画面(旅程、候補、割り勘、メンバー)・招待と参加申請・旅の設定・公開しおり・アカウント設定・リアルタイム更新 |
| 対象外: 本番のログイン | 会員登録・メールアドレスでのログイン・パスワード再設定は未実装(AWS への公開時に Amazon Cognito で作る)。試験では開発用ログインを使う |
| 対象外: AWS 上での試験 | 未公開のため。AWS の上限との比較は計算で示す |
| 対象外: 本物の Google マップへの負荷 | 外部のサービスに負荷をかけないため、試験では仮の地図・場所検索を使う。本物は手動で最小限を確認する |
| 対象外: 実機のスマートフォン | 画面幅とブラウザエンジン(WebKit)で代用する。実機の動作を保証するものではない |

## 3. テストの種類

| 種類 | 道具 | 確かめること |
|---|---|---|
| 単体テスト | Vitest | 計算、入力の確認、再接続などの部品 |
| 結合テスト | Vitest + DynamoDB Local | API、権限、同時更新、通知 |
| E2E テスト | Playwright + axe | 画面からの一連の操作、見やすさ |
| 負荷試験 | k6 | 応答時間、エラー率、通知の到達、限界、整合性 |
| 静的検査 | Biome、TypeScript、pnpm audit | 書き方、型、依存部品の脆弱性 |

## 4. E2E テスト

### 4.1 範囲
| 観点 | 内容 |
|---|---|
| 操作の網羅 | 画面上のすべての操作(追加・変更・削除・承認・公開・退会など)に、対応するテストがある |
| 一連の流れ | 3 人で「作成 → 招待 → 計画 → 投票 → 割り勘 → 公開 → 引き継ぎ → 退会」 |
| 失敗時 | 通信断、サーバーエラー、見つからない、同時更新の衝突、入力の上限、二重押し |
| 見やすさ | キーボードだけの操作、読み上げ用の名前、文字のコントラスト |

### 4.2 環境
Chromium、Firefox、WebKit、スマートフォン幅の 4 つ。

### 4.3 合格基準
| 項目 | 基準 |
|---|---|
| 成否 | 4 つの環境すべてで失敗 0 |
| 網羅 | 対応表に未実施の操作が 0 |
| 安定性 | Chromium で 10 回、ほかの環境で 3 回繰り返して失敗 0 |
| 見やすさ | axe の重大(serious・critical)な指摘 0。文字のコントラスト比 4.5 以上 |

## 5. 負荷試験

### 5.1 環境
負荷試験専用のデータベース(DynamoDB Local)と API を 1 台のパソコン上に立てる。普段の開発用データ、Google、AWS には負荷をかけない。
負荷をかける側と受ける側が同じパソコンで動くため、得られる値は **AWS 上の性能を保証するものではない**。

### 5.2 項目と合格基準
p95 は「100 回のうち 95 回がこの時間以内」を意味する。

| # | 試験 | 条件 | 合格基準 |
|---|---|---|---|
| L1 | 基準 | 1 人が全 API を 1 分間 | エラー 0 |
| L2 | 通常 | 100 人が 20 の旅。読み 9:書き 1。1 人 1 秒に 1 操作。10 分 | エラー率 1% 未満、読み p95 500ms 以内、書き p95 1 秒以内 |
| L3 | 集中 | 50 人(1 つの旅の上限)が同じ旅に WebSocket で接続。2 秒に 1 回の変更。5 分 | 通知の欠け 0、変更から全員の読み直し完了まで p95 2 秒以内 |
| L4 | 限界探し | L2 の操作で 50 → 100 → 200 → 400 → 800 人 | 合否なし。L2 の基準を破った人数と原因を記録 |
| L5 | 最大データ | 予定 300・候補 100・支出 500 件。コメントを段階的に 6 万件(仕様上の上限)まで | 応答 6MB 未満(AWS Lambda の上限)、読み・削除とも 29 秒以内 |
| L6 | 整合性 | 50 人が同時に更新・投票・採用・承認。件数の上限ちょうどへの同時追加 | 更新の消失・二重登録・上限超え・精算のずれが 0 |
| L7 | 長時間 | 50 人が L2 の操作と WebSocket 接続を 30 分 | メモリ・接続数・応答時間が増え続けない。エラー率 1% 未満 |
| L8 | 一斉再接続 | 50 人が同時に切断し、すぐ再接続 | 10 秒以内に全員が復帰、残骸の接続 0 |

同時更新で仕様どおりに返る 409(衝突)はエラーに数えず、件数を別に記録する。

### 5.3 AWS の上限との比較
| 項目 | AWS の上限 | 比べる値 |
|---|---|---|
| Lambda の応答 | 6MB | 旅 1 件の最大の応答 |
| API Gateway の待ち時間 | 30 秒 | 最も遅い操作 |
| DynamoDB の 1 パーティションの読み取り | 毎秒 3,000 RCU | 変更 1 回あたりの読み取り量 |
| DynamoDB の 1 パーティションの書き込み | 毎秒 1,000 WCU | 集中時の書き込み量 |

## 6. 不具合の扱い
| 優先度 | 目安 | 扱い |
|---|---|---|
| 高 | 安全面、データが壊れる、使えない | 修正して再試験 |
| 中 | 使いにくい、古い内容が表示される | 修正して再試験。仕様の判断が要るものは協議 |
| 低 | 整理、文書 | 可能な範囲で修正 |

修正は、不具合を再現するテストを先に書き、失敗を確かめてから行う。修正後は、関係する試験を同じ条件で再実施し、修正前後の結果を並べて記録する。
